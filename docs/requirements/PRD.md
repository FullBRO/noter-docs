# Noter — Product Requirements Document

**Status:** Baseline v1.0 — agreed MVP scope  
**Product:** Noter  
**Document type:** Product requirements

## 1. Product overview

Noter is a self-hosted, API-first personal information storage service. It provides one dependable place to capture, store, and retrieve information from different clients.

The initial product is a backend service. Its first interfaces are an HTTP API and, eventually, a command-line client. Desktop and mobile clients may be developed later without changing the backend into a client-specific application.

The backend is the source of truth. Clients are replaceable consumers of the API.

## 2. Product goals

The product is designed around the following priorities, in order:

1. **Reliability** — stored information should be durable and retrievable; successful writes must not be acknowledged before they are committed.
2. **Extensibility** — the design should allow future clients and capabilities without requiring a fundamental redesign.
3. **Simplicity** — the MVP should remain small and understandable; avoid infrastructure and abstractions without a current need.
4. **Speed** — performance matters, but it is secondary to the priorities above.

Noter is initially intended for one owner and self-hosted deployment. It is not a multi-tenant hosted service in the MVP.

## 3. Target user and use cases

The initial user is the owner of a private Noter installation. The service should support capturing and retrieving varied personal information, including:

- short snippets and reminders;
- lesson and study notes;
- code snippets;
- longer text documents;
- text containing Markdown syntax, stored as ordinary text.

The MVP does not interpret note content according to its format. For example, Markdown is stored as text; rendering, syntax-aware editing, and document semantics belong to future clients or future product capabilities.

## 4. MVP scope

### 4.1 In scope

- Create a note.
- List notes, newest first.
- Retrieve one note by its ID.
- Optional note title.
- Optional reusable tags.
- API-key authentication.
- Multiple independently revocable API keys.
- Cursor-based pagination for the note list.
- Idempotency support for note creation when the client supplies an idempotency key.
- OpenAPI specification for the HTTP API.
- Health endpoints for deployment monitoring.
- Database migrations, structured logging, automated tests, and documented backup/restore procedures.

### 4.2 Explicitly out of scope for the MVP

- Updating notes.
- Deleting notes through the API.
- Searching note content.
- Filtering notes by tags or other criteria.
- File uploads and attachments.
- Note version history.
- Backlinks and graph relationships between notes.
- Multiple user accounts, registration, or multi-tenancy.
- Web, desktop, or mobile applications.
- Client synchronization or offline conflict resolution.
- A complete CLI client.
- Streaming individual notes or terminal-oriented pagination.
- Distributed services or additional infrastructure such as Redis, Kafka, or Elasticsearch.

These exclusions describe the MVP, not necessarily the long-term direction of the product.

## 5. Functional requirements

### FR-01 — Create a note

The API must allow an authenticated client to create a note.

A note has:

- **Content:** required plain text, encoded as UTF-8.
- **Title:** optional text, with a maximum length of 200 characters.
- **Tags:** optional list of tag names, with no more than 20 tags associated with one note.
- **Creation timestamp:** assigned by the server.
- **ID:** generated by the server and unique within the installation.

The content must be stored and returned without application-level rewriting, trimming, Markdown rendering, or whitespace normalization. The maximum content size is **1 MiB (1,048,576 bytes)** measured as UTF-8 bytes. This is a configurable starting limit, not a database schema limit; the limit must be possible to increase through configuration without redesigning the note table.

The API must reject a note whose content exceeds the configured limit.

### FR-02 — Tags

Tags are optional and reusable across notes.

Tag identity is case-insensitive: names that differ only by letter case must resolve to the same logical tag. Tag names are normalized for identity and duplicate tags must not be created merely because their capitalization differs.

A note may have at most 20 tags. The system must enforce this limit when creating a note.

The exact Unicode normalization algorithm, display-name policy, maximum individual tag-name length, and behavior for duplicate tag values in a single request are implementation details to document before or during implementation. They must not weaken the case-insensitive uniqueness requirement or the 20-tags-per-note limit.

### FR-03 — List notes

The API must return notes ordered newest first. Ordering must be deterministic when multiple notes have the same creation timestamp.

The list response must use cursor-based pagination. The default page size is 20; the MVP supports page sizes of 10 or 20. The client must be able to request the next page using an opaque cursor returned by the previous response.

Each list item contains:

- note ID;
- optional title;
- creation timestamp;
- tags;
- a short content preview.

The list endpoint must not return the complete note content. The preview length and exact whitespace treatment are API presentation details; preview generation must never modify the stored content.

### FR-04 — Retrieve a note

The API must return a note by ID, including its complete original content, optional title, creation timestamp, and tags.

If the ID is valid but no note exists, the API returns `404 Not Found`.

### FR-05 — Authenticate API requests

All `/api/v1` endpoints must require an API key supplied as a bearer token:

```http
Authorization: Bearer <API_KEY>
```

The installation may have multiple API keys so different clients can use separate credentials. Each key must be independently revocable.

API keys are generated using a cryptographically secure random source. The raw key is displayed to the operator once at creation and is not stored in the database. Only a cryptographic hash of the key is stored. Key creation and revocation are performed using a local administrative command; the MVP does not expose HTTP endpoints for managing API keys.

There is no user registration or multi-user authorization model in the MVP.

### FR-06 — Idempotent note creation

`POST /api/v1/notes` must support an optional `Idempotency-Key` request header.

When a client supplies the header, retrying the same creation request with the same key must not create a second note. The idempotency state must be persisted so that the behavior survives process restarts.

Reusing the same key with a different request payload must be rejected with a conflict response. The detailed persistence and concurrency behavior is defined in the SAD.

If the client omits the header, the endpoint follows normal create semantics; clients that need safe retry behavior should supply it.

### FR-07 — Health checks

The service must expose:

- `GET /health/live` — indicates that the application process is running.
- `GET /health/ready` — indicates whether the service is ready to handle requests, including checking database connectivity.

These operational endpoints do not require an API key.

## 6. HTTP API surface

All application API endpoints are versioned under `/api/v1`.

| Method | Endpoint | Purpose | Authentication |
|---|---|---|---|
| `POST` | `/api/v1/notes` | Create a note | Required |
| `GET` | `/api/v1/notes` | List notes with cursor pagination | Required |
| `GET` | `/api/v1/notes/{id}` | Retrieve a note | Required |
| `GET` | `/health/live` | Liveness check | Not required |
| `GET` | `/health/ready` | Readiness check | Not required |

The API must publish an OpenAPI specification. The exact URL at which interactive API documentation is exposed is an implementation/deployment choice.

There are no note update or delete endpoints in the MVP.

## 7. Non-functional requirements

### 7.1 Reliability and durability

- A successful create response must only be returned after the database transaction has committed.
- Creating a note and associating its tags must be atomic: either all of the operation is committed or none of it is.
- Idempotency state, when supplied, must be committed atomically with the note creation.
- Database constraints must protect key uniqueness and relational integrity.
- Schema changes must be managed through versioned database migrations.
- Backup and restore procedures must be documented and a restore must be tested.

### 7.2 Security

- Production traffic must use HTTPS.
- API keys must not be stored in plaintext.
- API keys, authorization headers, note content, and other sensitive payload data must not be written to application logs.
- Input must be validated and request body size limited.
- CORS must be disabled or restricted to explicitly configured origins; it is not needed for the initial CLI/API use case.

### 7.3 Maintainability

- The application must use strict TypeScript settings.
- The codebase must be organized as a modular monolith with clear module responsibilities.
- The HTTP API must be described with OpenAPI.
- Automated tests must cover core behavior, authorization, persistence, and pagination.
- CI must run quality checks and tests before changes are merged.

### 7.4 Deployment

- The service must be deployable on a Linux host using Docker Compose.
- PostgreSQL is the persistent source of truth.
- Configuration must be provided through environment variables rather than hard-coded deployment-specific values.
- Database migrations must have a production-safe deployment procedure.

## 8. Data ownership and retention

The MVP is a single-owner installation. Notes are append-only through the public API: once created, a note cannot be updated or deleted through the MVP API.

The operator is responsible for protecting and backing up the installation's database and deployment secrets. Backup material should be stored separately from the primary database volume.

## 9. Acceptance criteria

The MVP is acceptable when all of the following are true:

1. An authenticated client can create a text note with a required content field.
2. A note can optionally have a title of up to 200 characters.
3. A note can optionally have tags, and no note can have more than 20 tags.
4. Tag identity is case-insensitive and tags can be reused across notes.
5. Content larger than the configured byte limit is rejected; the default is 1 MiB.
6. A client can list notes newest first using cursor pagination, with the supported page sizes.
7. List responses include note metadata, tags, and a short preview rather than the full content.
8. A client can retrieve a note by ID and receive its complete original content.
9. Missing or invalid API keys are rejected for `/api/v1` endpoints.
10. An operator can create and revoke independent API keys using a local administrative command.
11. A note creation request with an idempotency key can be safely retried without creating duplicate notes; reuse with a different payload is rejected.
12. Note, tag associations, and idempotency state are written atomically where applicable.
13. Automated tests cover the core API and persistence behavior.
14. The application can be deployed using the documented Docker Compose procedure.
15. The backup can be restored using the documented procedure, and that procedure has been tested.
16. OpenAPI documentation is generated from or kept in sync with the API implementation.

## 10. Deferred decisions

The following details are intentionally not product-scope blockers and can be finalized in implementation notes or ADRs:

- exact tag-name maximum length and duplicate-tag input behavior;
- exact preview length and whitespace presentation;
- exact interactive OpenAPI documentation URL;
- API-key expiration policy;
- rate limiting and abuse protection beyond basic request validation;
- backup encryption and off-site retention policy, based on the hosting environment;
- future search, update/delete, attachment, and client application capabilities.
